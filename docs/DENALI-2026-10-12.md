# Denali USB4 Bring-Up: Pinmux, Firmware, and GCC Analysis
# Date: 2026-10-11 to 2026-10-12
# Surface Pro 11 (X1P-64100, Denali) — Arch Linux

## Summary

This document records the overnight reverse-engineering work to bring up the
USB4 controller on the Surface Pro 11 (Snapdragon X1P-64100, "Denali").
Two major breakthroughs were achieved; the final UC power-up remains blocked
on Denali-specific clock/power details.

**Achieved:**
1. Sideband pinmux fixed (6 GPIOs muxed via custom MMIO kernel module)
2. UC firmware extracted from Windows driver (SHA256-verified)

**Blocked:**
- UC power domain at 0x15600000 does not respond to MMIO writes
- GCC located at 0x100000 (via Ghidra decompilation)
- 17 USB4 clocks enabled, both GDSCs ON, but UC remains dark
- Denali-specific power sequence unknown; X1E80100 offsets insufficient

---

## 1. Pinmux Fix (2026-10-11 ~23:00)

### Problem
The USB4 sideband pins (gpio163-165 for USB0, gpio172-174 for USB1) were
UNCLAIMED in the Denali device tree. The UC (microcontroller) waits for
sideband RX forever if the pins are not muxed to the USB4 function.

### Solution
Wrote an out-of-tree MMIO kernel module (`denali-tools/kmod/mmio.c`) to
bypass `STRICT_DEVMEM`, exposing `/dev/mmio` for root physical read/write.
Used Python helper (`denali-tools/mmio.py`, corrected to `_IOR/_IOW` size 16,
`<QII` packing) to write TLMM registers directly.

### TLMM Writes (volatile, lost on reboot)
TLMM base: 0x0f100000

| GPIO | Original | Written | Function |
|------|----------|---------|----------|
| 163 | 0x00000001 | 0x00000230 | usb0_sbrx |
| 164 | 0x00000001 | 0x00000337 | usb0_sbtx |
| 165 | 0x00000200 | 0x00000334 | (sideband) |
| 172 | 0x00000001 | 0x00000240 | usb1_sbrx |
| 173 | 0x00000001 | 0x00000347 | usb1_sbtx |
| 174 | 0x00000200 | 0x00000344 | (sideband) |

**WARNING:** The function IDs (140/141/144/145) from debugfs are pinctrl-driver
logical indices, NOT verified raw TLMM mux selector values. These writes were
experimental and have not been validated against Qualcomm's pinctrl tables.
Do not treat as a proven fix without further verification.

Verification was via register readback only; debugfs still showed UNCLAIMED
(which is expected — debugfs reflects the pinctrl driver state, not the raw
hardware).

### Module Details
- Source: `denali-tools/kmod/mmio.c`
- Device: `/dev/mmio`, mode 0600, root only
- **SECURITY:** Exposes unrestricted physical memory access. Unload/remove
  when not needed. Not configured to persist across reboot.
- Kernel tainted by unsigned module.

## 2. Firmware Extraction (2026-10-11 ~23:42)

### Source
Windows driver from Surface Pro 11 driver MSI:
- File: `QcUsb4Filter.sys` (from `SurfacePro11_ARM_Win11_26100_26.041.12746.0.msi`)
- Version: 1.0.4196.6900, built Nov 24 2024
- Size: 524,504 bytes, AArch64 PE
- Local copy: `~/workspace/usb4-denali/_dl/QcUsb4Filter.sys` (gitignored)

### Discovery Method
Birk's `snapshot/module/frontend.c` contains:
```c
ret = request_firmware_direct(&p->fw, "qcom/x1-diag-mcu.bin", dev);
if (p->fw->size != 40816 || memcmp(digest, firmware_sha256, sizeof(digest))) {
```
With SHA256:
```
cd4f5929b51f2dbb0b583693ff8d024521c87f0d2e45c7adc142fed976650b99
```

Searched the driver binary for a 40816-byte region matching this hash.
Found at **file offset 0x4b9c0**.

### Firmware Details
- Filename: `qcom/x1-diag-mcu.bin` (DIAG firmware, not production)
- Size: 40816 bytes
- SHA256: `cd4f5929b51f2dbb0b583693ff8d024521c87f0d2e45c7adc142fed976650b99`
- Format: 2 records of `(u32 offset, u32 word_count, u32 words[])`
  - Record 1: offset=0x0, words=7840
  - Record 2: (second record)
- Saved to: `~/workspace/usb4-denali/_dl/x1-diag-mcu.bin` (gitignored)
- Copied to Surface: `/home/kyjus25/x1-diag-mcu.bin`

### Prior Failed Attempts
Exhaustive static analysis found no firmware in plain form:
- Strings, entropy scans, PE section analysis
- Birk's `(offset,count,words)` validator (all offsets/sizes)
- MMIO table analysis, disassembly (capstone), import analysis
- XOR brute-force (single byte), LZMA probes, Thumb code scan
- Alternative formats (u16/u16, addr/len), MSI package scan (435 files)

The firmware WAS present but not in plain `(offset,count,words)` form at
arbitrary offsets — it required the SHA256 to locate.

## 3. Ghidra Reverse Engineering (2026-10-12)

### Setup
- Ghidra 11.0.3 (~/workspace/ghidra_11.0.3_PUBLIC, 1.1GB)
- Temurin JDK 17.0.9 (~/workspace/jdk-17.0.9+9)
- Project: /tmp/ghidra_proj/QcUsb4Filter
- Headless analysis completed

### Key Findings

#### MMIO Mapper Function: FUN_14005c3c0
Decompiled the WDF driver's hardware init callback. It calls
`MmMapIoSpaceEx` 7 times:

| Physical Address | Size | Purpose | Stored At |
|------------------|------|---------|-----------|
| 0x15600000 | 0x100000 | UC/router | lVar6+0x10 |
| 0x100000 | 0x200000 | **GCC** | lVar6+0x20 |
| 0x1fc0000 | (var) | Clock controller | lVar6+0x60 |
| 0xf100000 | (var) | TLMM | lVar6+0x70 |
| (variable) | (var) | Unknown | lVar6+0x30 |
| (variable) | (var) | Unknown | lVar6+0x40 |
| (variable) | (var) | Unknown | lVar6+0x50 |

**Critical:** The GCC is at **0x100000**, NOT 0x34980000!
The "MMIO table" at file offset 0x4531e (containing 0x34980000 etc.)
is NOT used for the main mapping. Those addresses may be for a
different purpose or are stale.

The 0x100000 address matches the Device Tree: `clock-controller@100000`.

#### DriverEntry Chain
- `entry @ 14003f020`: calls FUN_14007d2f8(), FUN_14003f070()
- `FUN_14003f070 @ 14003f070`: DriverEntry
  - `WdfVersionBind`, `WdfDriverCreate` (FUN_14003f400)
  - `FUN_14003f300` (device setup)
  - `FUN_14007d000` (EvtDriverDeviceAdd)
- `FUN_14007d000`: registers callbacks including FUN_14005bc30
- `FUN_14005bc30`: registers 5 callbacks:
  - FUN_1400150a0, FUN_140015e10, FUN_1400165f0
  - FUN_14005c3c0 (the MMIO mapper — does the MmMapIoSpaceEx calls)
  - FUN_14005d4a0 (cleanup — calls MmUnmapIoSpace)

The driver does NOT write to GCC registers directly in the decompiled
mapper function. Clock/power setup is likely handled by the Windows
power framework (PoFx), not the driver. This explains why the exact
Denali sequence is not easily extractable from the binary.

## 4. GCC Clock Analysis (2026-10-12)

### GCC Accessibility
- Base: 0x100000 — **READABLE** via /dev/mmio
- The 0x1fc0000 region: **NOT ACCESSIBLE** (bus fault, segfault)

### USB4 Clocks Enabled
Using X1E80100 offsets from `gcc-x1e80100.c` (which work on Denali for
read/write, but may not be sufficient):

**USB4_0 (0x9fxxx):**
| Offset | Name | Before | After |
|--------|------|--------|-------|
| 0x9f0a8 | ahb_clk | 0x80000000 | 0x80000001 |
| 0x9f054 | sys_clk | 0x80004000 | 0x80004001 |
| 0x9f018 | master_clk | 0x80000000 | 0x80000001 |
| 0x9f044 | sb_if_clk | 0x80000000 | 0x80000001 |
| 0x9f088 | tmu_clk | 0x82000000 | 0x82000001 |

**USB4_1 (0x2bxxx):**
| Offset | Name | Before | After |
|--------|------|--------|-------|
| 0x2b0a8 | ahb1_clk | 0x80000000 | 0x80000001 |
| 0x2b054 | sys1_clk | 0x80004000 | 0x80004001 |
| 0x2b018 | master1_clk | 0x80000000 | 0x80000001 |
| 0x2b044 | sb_if1_clk | 0x80000000 | 0x80000001 |
| 0x2b088 | tmu1_clk | 0x82000000 | 0x82000001 |

**Additional clocks enabled:**
0x9f060, 0x9f0a4, 0x9f0b0, 0x9f0c0, 0x9f0cc, 0x9f0d0, 0x9f0d8

Total: 17 clocks enabled.

### GDSC Status
- USB4_0 GDSC @ 0x9f004: 0x0022f801 (bit 0 = 1, **ON**)
- USB4_1 GDSC @ 0x2b004: 0x0022f801 (bit 0 = 1, **ON**)
- USB4_0 BCR @ 0x9f000: 0x00000000 (not in reset)

### Result
Despite power (GDSC ON) and 17 clocks enabled, the UC at 0x15600000
does NOT respond to MMIO writes (reads return 0, writes don't stick).

## 5. Blocker: Denali-Specific Power Sequence

The X1E80100 clock offsets are readable/writable on Denali, but they are
not sufficient to power the UC. Denali (X1P64100) likely has:
- Different GDSC offsets, OR
- Additional power domains, OR
- Different reset controls, OR
- A completely different init sequence

The Windows driver does not contain the GCC write sequence in an easily
extractable form (Windows power framework handles it). Without the
Denali TRM or dynamic analysis on Windows, the exact sequence cannot
be derived.

### What Was Tried
- Probed GCC 0x9f000-0x9f100: found clocks, enabled 12
- Probed USB4_1 at 0x2bxxx: found GDSC and clocks, enabled 5
- Checked BCR: already deasserted
- Checked UC gates at +0xd064, +0x8018: unreadable (domain off)
- Wide GCC probe: segfault on invalid regions

1. **Community**: Ask Birk (birkskyum) or linux-surface for Denali GDSC offsets.
   The X1P64100 TRM is not public.
